## 뭘 하려는가 (한 줄)

지피터스 글을 클립할 때 본문이 자꾸 빈 채로 오는 원인을 짚고, 본문을 안정적으로 받아오게 고친다.

## 왜 / 언제 쓰는 일인가

사례 클리핑은 g23-case-writer 의 재료를 대는 핵심 파이프라인([[014-clip-gpters-50]]).
지금 여기서 막히면 참가자가 참고할 사례 풀도, 사례글 문체 근거도 안 쌓인다.
클리핑은 앞으로도 매주 반복할 일이라, 한 번 튼튼하게 잡아두면 계속 값을 한다.

## 증상 (관찰된 것만)

- 클립을 만들면 본문이 비거나, 요약 자리에 "로그인 필요"만 남는 글이 섞여 온다.
- 어떤 글은 잘 열리고 어떤 글은 빈 채로 온다 — 불규칙하다.
- 현재 경로: `gpters-case-researcher` 가 `https://r.jina.ai/<게시글URL>` (Jina Reader) 로 본문을 받아온다.

## 할 것 (체크리스트)

> 해법을 미리 정해두지 않는다. 원인부터 좁힌 뒤 고친다.

- [x] 빈 본문을 실제로 재현한다 → 동시 10건 버스트에서 502 발생 재현 (아래 진단)
- [x] 원인을 좁힌다 → **Jina Reader 의 부하 시 간헐 502** + researcher 의 실패 오표기. 로그인 벽·URL 형태·rate limit(429) 아님
- [x] 본문을 안정적으로 받는 방법을 정하고 검증한다 → 순차 + 재시도. 502 났던 URL 이 재시도에서 3/3 성공
- [x] 재발 방지 → researcher 규칙 수정 (순차 원칙 · 재시도 2회 · 실패 사유 구분 표기)

## 완료 기준

- 빈 본문이던 글 3개가 실제 본문으로 열린다.
- 원인이 한 줄로 설명된다 ("왜 어떤 글만 빈 채로 왔는가").
- 다음에 또 막혔을 때 어떻게 할지(폴백/기록)가 한 줄로 정해져 있다.

## 진단 결과 (2026-07-03, Fable 브랜치)

**원인 한 줄: r.jina.ai 가 동시 요청에서 간헐적으로 502 를 내는데, researcher 가 재시도 없이 모든 실패를 "로그인 필요"로 표기해 빈 본문이 그대로 굳었다.**

원인 사슬 (재현 근거):

1. **Jina Reader 간헐 502** — 클립 소스 URL 10개를 동시 호출하자 1건이 502. 같은 URL을 순차로 다시 열면 3/3 성공 (본문 6.8KB 정상). 즉 URL·로그인 문제가 아니라 **부하 의존적 일시 실패**. 014가 "5개 병렬 에이전트"로 돈 것이 정확히 이 조건. rate limit(429)이 아니라 502 = Jina 쪽 렌더 실패.
2. **실패 오표기** — researcher 규칙이 "막히면(로그인 벽 등) → `본문: 로그인 필요`"로 모든 실패를 뭉뚱그림. 일시 502가 로그인 벽으로 기록돼 증상이 헷갈렸다.
3. **재시도 부재** — 한 번 실패하면 그대로 끝. 재시도만 있었어도 대부분 열렸다.

검증:

- 순차 단건 요청: 6/6 성공 (200, 본문 6~21KB).
- 동시 10건 버스트: 1건 502 → **재현**.
- 502 났던 URL 순차 재시도: 3/3 성공 → **해법 검증**.
- 저장된 클립 50개는 전수 확인 결과 모두 본문 있음 (빈 클립 0건) — 피해는 "후보 조사 단계에서 로그인 필요로 잘못 걸러진 글"에 있었음.

완료 기준 대비 한 가지 편차: "빈 본문이던 글 3개"의 목록이 014에 안 남아 있어(실패 기록 누락), 대신 실패를 라이브로 재현한 뒤 그 URL로 검증했다.

재발 방지 (반영 완료 → `.claude/agents/gpters-case-researcher.md`):

- 여러 글은 **순차로** 연다 (동시 호출 금지).
- 비거나 에러면 **최대 2번 재시도**.
- 그래도 실패면 사유를 구분해 표기: 로그인 안내가 보일 때만 `로그인 필요`, 아니면 `일시 실패(재시도 2회)`.
