## 방법

표본 게시글 5개를 **원본 URL 직접**과 **Jina Reader 경유(`r.jina.ai/<URL>`)** 두 경로로 각각 WebFetch,
빈 본문/오류 발생을 관찰. 502가 난 건 1회 재시도.

## 관찰 데이터

| 글 | 원본 직접 | Jina 경유 |
|---|---|---|
| 1 nocode/story-how-we-designed | ✅ 본문 | ✅ 본문 |
| 2 dev/improvement-loop | ❌ 502 (재시도도 502) | ✅ 본문 |
| 3 wealth/government-project | ✅ 본문 | ❌ 502 → **재시도 ✅** |
| 4 nocode/3-things-did-follow | ❌ 502 | ✅ 본문 |
| 5 marketing/creating-landing-page | ❌ 502 | ✅ 본문 |

- **원본 직접 성공률: 2/5 (40%)** — 502가 잦다.
- **Jina 경유 성공률: 첫 시도 4/5, 재시도 포함 5/5 (100%)** — 훨씬 안정적.
- 글3: Jina 1차 502였다가 **재시도에서 열림** → 502는 영구 실패가 아니라 일시 오류.

## 원인 (한 줄)

빈 본문 = **SPA 렌더 실패가 아니라 간헐적 502 Bad Gateway**. 원본 직접은 502가 잦고 Jina 경유가 안정적인데,
현재 규칙은 Jina 단일 경로 + **재시도 없음**이라 Jina가 502를 내는 순간의 글이 그대로 빈 본문으로 남는다.
게다가 502를 "로그인 필요"로 오표기하면 재시도 가능한 실패와 접근 불가가 뒤섞인다.

## 해법 (제안)

1. **Jina 경유 유지** — 원본 직접(40%)보다 안정적(100%). 현행 방향은 맞다.
2. **502/빈 응답 시 1~2회 재시도** (짧은 간격). 재시도로 대개 풀린다(글3 실증).
3. **동시 요청 수 제한** — 병렬로 다발 요청하면 502가 늘어나는 정황(6개 동시 던졌을 때 다발 발생). 워커 동시성 3~5로 제한.
4. **실패는 정확히 기록** — 재시도까지 실패하면 `본문: 로그인 필요`가 아니라 `본문 실패(502)` 로 남겨,
   재시도 대상과 진짜 접근 불가를 구분한다.

- 추가: "여러 글을 동시에 열 때 한 번에 3~5개까지만 — 과도한 동시 요청은 502를 유발한다."
