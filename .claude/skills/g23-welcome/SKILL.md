# g23-welcome — 첫날 업무 사례 + 4주 로드맵

`g23-setup`으로 작업 공간 준비와 k-skill 설치·체험을 마친 참가자가, 자기 업무를 지피터스 사례와 연결해 **4주 자동화 로드맵 HTML**을 손에 쥐는 단계다.
①~③을 이 파일에서 진행하고, ④에서 OT 사례글 초안은 `g23-case-writer`, 마지막 주차 안내는 `g23-missions`로 넘긴다 — welcome이 초안을 직접 쓰지 않는다.

## 시작 전 확인 (setup 완료 전제)

이 skill은 `g23-setup`(정체성 기록·git 초기화·k-skill 설치·체험)이 끝난 뒤에 이어진다.
- `CLAUDE.local.md`에 정체성 블록(성함·목적·파일명 닉네임)이 없으면 셋업이 아직 안 끝난 것이다. 참가자에게 **"스터디 시작 도와줘"** 라고 말해 `g23-setup`부터 진행하도록 안내하고 여기서 멈춘다.
- 정체성 블록이 있으면 그 파일명 닉네임을 로드맵 HTML 파일명(`gpters-k-skill-report-{닉네임}.html`)에 쓴다.

## 진행 순서 (①→④)

이미 끝난 항목은 건너뛰고, 필요한 것만 대화형으로 확인한다. 한 번에 한 단계씩 질문은 짧게 한다.
시간이 부족하면 실제 게시글 발행부터 생략한다. welcome에서 4주 자동화 HTML까지 남기고, OT 초안은 ④에서 `g23-case-writer`로 이어 만든다.

### ① 업무 파악 (10분)

`CLAUDE.local.md`의 정체성·목적을 다시 묻지 말고, 4주 로드맵에 쓸 업무 맥락만 확인한다.
- 어떤 일을 하나요? (직무/업무 성격)
- 매일·매주 반복되는 작은 작업 몇 가지는?
- 4주 동안 자동화하고 싶은 것, 지금 Claude Code로 해보고 싶은 것 하나는?

원하면 이 업무 맥락을 `CLAUDE.local.md`의 정체성 블록 아래 짧은 문단으로 **제안**해 함께 반영한다 (성함·목적을 다시 묻지 않는다). 원치 않으면 그대로 둔다. `CLAUDE.md`(공용 가이드)에는 쓰지 않는다.

### ② 관련 지피터스 사례 검색 (10분)

- `data/README.md`와 각 파일의 제목·태그·핵심 요약으로 후보를 먼저 좁힌다. 원문 전문 63개를 통째로 읽지 않는다.
- 관련성이 높은 사례 2~3개만 열어 참가자의 목표와 닮은 점, 빌릴 점, 버릴 점, 원문 URL을 뽑는다.
- 로컬 `data/`로 딱 맞는 사례가 안 나오면 `gpters-case-researcher`에 위임해 후보를 넓게 받아온다 (CLAUDE.md 표준 위임 규칙).

### ③ 4주 자동화 로드맵 HTML (10분)

`reference/gpters-k-skill-report-template.html`을 읽고 루트 `gpters-k-skill-report-{닉네임}.html`로 채운다.
- 참가자 입력과 사례 텍스트는 HTML escape한다.
- **week-1**은 오늘 한 것으로 쓴다 — k-skill 설치·체험과, ①에서 나온 "만들어보고 싶은 첫 skill" 아이디어.
- week-2~4는 참가자 목표를 향한 작은 가설·후보로 쓰고, 아직 만들지 않은 skill을 확정 약속처럼 표현하지 않는다.
- 사례는 실제로 읽은 2~3개만 넣고 원문 URL을 클릭 가능한 링크로 남긴다.
- `{{next_step}}`에는 4주 로드맵을 다음으로 잇는 짧은 표시를 넣는다. "2주차"라는 말을 여기 직접 쓰지 않는다 — 바로 아래 로드맵 week-2 카드(개인 계획)와 첫눈에 뭉개진다. 2주차에 무엇을 하는지는 "2주차 미션 알려줘"(→ `g23-missions`)로 안내한다.
- 스타일은 `reference/design-gpters.md`를 읽고 그 색·폰트·표 규칙을 따른다. 외부 CSS·JS·폰트·이미지는 넣지 않는다.
- 생성 직후 `reference/roadmap-html-validation.md`를 읽고 빠른 검사를 통과시킨 뒤 브라우저로 연다. 자동으로 못 열면 파일 링크와 위치를 알려준다.
- 참가자가 보는 설명은 전문용어를 나열하지 않고, 일상어와 부담을 낮추는 쿠션어로 쓴다.

### ④ 핸드오프 — OT 초안(→ case-writer) · 2주차(→ missions)

welcome은 초안을 직접 쓰지 않는다. 로드맵 HTML까지 손에 쥐었으면, 참가자가 스스로 다음 두 skill을 켜도록 순서대로 안내한다.

1. 오늘 손에 남은 것을 한 줄로 요약한다: `gpters-k-skill-report-{닉네임}.html` (4주 자동화 로드맵).
2. OT 사례 초안은 `g23-case-writer`로 넘긴다. 다음 문장을 준다:
   > 이제 **"OT 사례 초안 써줘"** 라고 말해보세요. `g23-case-writer`가 오늘 한 것(k-skill 체험·지피터스 사례·4주 계획)으로 짧은 OT 초안을 만들어 파일로 남겨줘요.
   - 필수 완료선은 OT 초안까지다. 초안 작성·저장·발행 안내는 `g23-case-writer`가 맡는다(오늘 실제로 한 것만 담고, 아직 안 만든 skill의 효과는 지어내지 않는 규칙도 그 skill 안에 있다).
3. 이어서 2주차로 잇는다:
   > 그다음 **"2주차 미션 알려줘"** 라고 말하면 `g23-missions`가 로드맵의 다음 작은 행동과 연결해 안내해요.

## 하지 말 것
- 작업 공간 초기화(정체성 기록·git init·k-skill 설치·체험)를 여기서 하지 않는다 — 그건 `g23-setup`이다. 안 돼 있으면 setup으로 안내한다.
- 정체성·업무 맥락을 `CLAUDE.md`(스터디 공용 가이드)에 쓰지 않는다 — 개인 정보는 항상 `CLAUDE.local.md`.
- ① 업무 파악 답을 참가자 대신 해석해 `CLAUDE.local.md`에 바로 쓰지 않는다 — 제안하고 동의를 받는다.
- `data/*.md` 63개의 원문 전문을 통째로 읽지 않는다. 인덱스·태그·요약으로 좁힌 뒤 2~3개만 읽는다.
- HTML에 외부 CSS·JavaScript·폰트·이미지를 추가하거나 `{{...}}` placeholder를 남기지 않는다.
- OT 사례글 초안을 welcome이 직접 쓰지 않는다 — ④에서 `g23-case-writer`로 넘긴다.
- 참가자를 대신해 gpters.org에 발행하지 않는다.
- 참가자가 요청하지 않은 파일을 대량 생성하지 않는다. 첫날 welcome 자체 산출물은 `gpters-k-skill-report-{닉네임}.html`로 한정한다(OT 초안 파일은 `g23-case-writer`가 만든다).
