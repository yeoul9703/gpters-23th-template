## 1차 결론 (내가 처음 제안)

welcome은 손대지 말고(P1/A5 유지), skill-creator에서 실제로 Python이 필요해진 참가자에게만 온디맨드로 대응하자고 제안.

## 사용자의 반박 — 일관성 우려

온디맨드로만 대응하면 참가자마다 설치 방법이 제각각(conda, 시스템 pip --user, brew python, Windows py 런처 등)이라 트러블슈팅 비용이 매번 새로 든다. `uv venv`로 표준화하는 게 의미가 있는지 질문.

## 재정리한 논점

이건 "참가자에게 Python 셋업을 가르칠지"가 아니라 **"Claude Code가 즉석 Python이 필요할 때 어떤 방식으로 실행하게 할지 하나의 컨벤션으로 못박을지"** 문제로 보임.

- `uv run --with <pkg> script.py` (또는 PEP 723 인라인 의존성)는 venv 생성·activate·pip install 3단계를 없애고, 시스템에 Python이 없어도 uv가 알아서 받아온다. Windows/Mac 동일 명령.
- 이 컨벤션은 **모든 참가자에게 사전 교육할 필요가 없다** — uv 설치 자체도 온디맨드(필요해진 순간 skill-creator나 실행 중에 "uv 없으면 이 한 줄로 설치" 안내)면 충분. 즉 P1("Python 사전 교육 안 함")과 충돌하지 않으면서, 실제로 필요해진 소수 참가자 사이의 **실행 방식만 통일**하는 효과.
- 반대 근거: 스터디 규모(4주, Pro 요금제, 비개발자 다수)에서 Python이 필요한 케이스 자체가 드물 것으로 예상됨. 드문 케이스를 위해 미리 표준(uv)을 문서화해두는 비용 대비, 실제 마주쳤을 때 즉석으로 "uv 쓰세요" 한 줄 안내하는 것과 실질적 차이가 크지 않을 수 있음.

## advisor 결론

- **핵심 전제**: 일관성은 "uv가 머신에 있는지"가 아니라 "**Claude가 그 컨벤션을 읽는 위치가 있는지**"에서 나온다. 아무 데도 안 적혀 있으면 uv를 쓰든 안 쓰든 Claude의 즉석 Python 방식은 매번 달라진다 — "uv 채택"과 "Claude가 로드하는 어딘가에 한 줄 적어두기"는 분리 불가능한 하나의 결정.
- 이게 결정을 **빈도 → 문서 위치** 한 축으로 접는다:
  - 거의 안 씀 → 아무 것도 안 적고 1:1 대응 (내 1차 제안)
  - 드물지만 터지면 비용 큼 → **온디맨드 레퍼런스**(skill-creator가 실제 Python 필요 상황을 만났을 때만 참조) — 상시 로드 아님, welcome에도 안 넣음
  - 자주 씀 → 참가자용 CLAUDE.md에 상시 명문화 (P1과 가장 크게 충돌, 이 스터디엔 과함)
- **추천: 가운데.** 이 코호트(4주·Pro·비개발자 다수) 특성상 Python 실행 자체가 드물 것 — uv의 가치는 "일상적 편의"가 아니라 "터졌을 때 트러블슈팅 비용을 낮추는 보험" 성격. 과대평가하지 말 것.
- Windows/Mac 분기는 완전히 사라지지 않고 **줄어든다**: uv 설치 명령 자체는 OS별로 다름(Windows `irm https://astral.sh/uv/install.ps1 | iex`, Mac `curl -LsSf https://astral.sh/uv/install.sh | sh` 또는 brew). 그 한 줄 이후 `uv run --with <pkg> script.py`(또는 PEP 723 인라인 의존성)는 OS 무관 동일 — venv 생성/activate 없이 uv가 Python까지 받아옴. `uv venv`는 오히려 무거운 경로이고, 실제 이점은 `uv run --with` 쪽에서 나온다.

## 사용자의 2차 제안 — 셋팅 가이드 문서 + `g23-setup` 스킬 부활

"온디맨드 참고" 자체를 별도 스킬(`g23-setup`)로 만들면 어떤가 — 즉 advisor가 말한 "온디맨드 레퍼런스"를 skill-creator 안의 한 문단이 아니라 독립된 스킬로 구현하자는 아이디어.

### 중요한 선례 충돌

`g23-setup`은 **이미 한 번 존재했다가 삭제됐다** (task 010, 커밋 `9fae667`). 그런데 삭제 사유를 실제로 확인해보니:

- 옛 `g23-setup`의 내용은 지금 이 문서가 논의 중인 "OS별 설치 명령·Python·uv 가이드"가 **전혀 아니었음** — ①환경확인(OS만 물음, 분기 내용 없음) ②k-skill 준비 ③업무 파악 ④CLAUDE.md 개인화, 총 4단계로 지금 `g23-welcome`의 ①~④와 **거의 동일한 내용의 중복 스킬**이었다.
- A1 결정문: "setup 삭제 + 트리거 이전... 리다이렉트 파일 안 만듦(P1: 빈 껍데기 금지)". 즉 삭제 사유는 "콘텐츠가 나빠서"가 아니라 "welcome과 완전히 겹쳐서 빈 껍데기가 됐기 때문".
- 트리거 문구 "초기 설정/셋업/처음인데 뭐부터"는 **이미 welcome description으로 이전 완료** (README L19/L51, missions/week-1.md L11 갱신됨).

### 그래서 지금 제안은 "부활"이 아니라 "다른 것"

이번에 만들려는 건 온보딩 중복이 아니라 **Python/라이브러리 환경 문제가 실제로 터졌을 때만 켜지는 좁은 트러블슈팅 스킬** — advisor가 말한 "온디맨드 레퍼런스"의 스킬 버전. 콘텐츠도 다르고(uv 컨벤션 + OS별 설치 한 줄) 트리거도 달라야 함("Python 설치", "라이브러리 안 깔림", "uv" 등 — "셋업/초기 설정"은 이미 welcome 소유라 재사용하면 트리거 충돌).

### 미결 — advisor에게 물을 것

1. 이걸 **독립 스킬**로 만드는 게 맞나, 아니면 advisor가 이미 권한 "skill-creator 옆 참고 문단"으로 충분한가 — 스킬 하나 추가는 P1(스킬 목록 최소화, 6종 확정)과 다시 부딪힘.
2. 스킬로 간다면 이름을 `g23-setup`으로 재사용해도 되는지(과거 삭제 이력 때문에 헷갈릴 수 있음) 아니면 `g23-python-setup` 등 새 이름이 나은지.

## advisor 2차 결론

- **"가이드 문서"와 "스킬 래퍼"는 별개 결정.** 문서화는 이미 권한 사항(온디맨드 레퍼런스) 그대로 진행. **스킬로 승격하는 건 아직 아니다.**
- 이유: 스킬의 `description`은 트리거 매칭을 위해 **모든 세션에 상시 로드**된다 — Pro 요금제 토큰 절약(P1의 실제 근거)에서 "거의 안 쓰는 스킬의 상시 로드 비용"은 정확히 처음 g23-setup을 죽인 "빈 껍데기"의 현대판. 나중에 사용 빈도가 실제로 확인되면 frontmatter만 추가해 문서 → 스킬 승격은 쉬움 — 지금 미리 스킬 로스터 비용을 낼 이유 없음.
- **더 중요한 건 범위(scope)가 흐트러졌다는 것.** 이 스레드는 "Python은 드묾 → uv는 보험" 쪽으로 좁아졌지만, 사용자의 원래 질문·"셋팅 가이드 문서"라는 표현은 더 넓다(Windows/Mac 터미널, 라이브러리 설치 일반). 이 둘은 **빈도가 다르다**:
  - Python/uv 환경 도움 → **드묾**(소수 참가자) → 온디맨드 문서로 충분, 스킬은 과함.
  - Windows 터미널 선택("bash 전제 안 함") → **모든 Windows 참가자가 시작 시 한 번** 겪음 → 그런데 이건 welcome ①과 그대로 겹침 — 옛 g23-setup을 죽인 바로 그 중복.
  - 따라서 콘텐츠를 하나의 `g23-setup` 스킬에 묶으면 두 성격이 뒤섞이고 welcome과의 중복도 재발한다. **Windows 터미널 부분 = welcome/README 근처, Python/uv 부분 = 온디맨드 문서**로 집을 분리하는 게 맞다.
  - 그래도 스킬을 원한다면: 이름은 `g23-setup` 재사용 금지(트리거 "셋업/초기 설정"은 이미 welcome 소유라 활성화 모호해짐) — 새 이름 + 겹치지 않는 트리거("Python 안 깔려", "라이브러리 설치", "uv") 필요.
